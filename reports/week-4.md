### 기술 선택 재평가

* 다시 한다면 같은 기술? 왜?

다시 진행하더라도 MVP 단계에서는 **Android Native와 NFC를 우선 선택했을 것** 같다.

Android Native는 팀이 익숙하게 다룰 수 있는 기술이었고, NFC처럼 기기 하드웨어와 직접 통신해야 하는 기능을 구현할 때 원인을 파악하고 빠르게 테스트하기에 적절하다고 판단했다. MVP의 목적이 완성된 서비스를 만드는 것이 아니라, NFC 방식이 기존 출석 과정의 불편함을 줄일 수 있는지 빠르게 검증하는 것이었기 때문에 익숙한 기술을 선택한 것은 적절했다.

다만 NFC라는 방식 자체는 다시 선택하더라도 더 신중하게 검토했을 것 같다. 처음에는 NFC가 기존 출석 앱의 불편함을 대부분 해결할 수 있을 것이라고 생각했지만, 테스트를 통해 앱 실행 필요, 태그 위치 이동, 특정 시간대 병목 가능성, 실제 출석 서버의 사내망 의존성 같은 한계도 확인했다. 따라서 다시 한다면 NFC를 바로 해결책으로 확정하기보다, 기존 출석 과정의 불편을 더 세분화한 뒤 NFC가 해결할 수 있는 문제와 해결하지 못하는 문제를 먼저 구분했을 것 같다.

* 고려했다 안 쓴 선택지와 뺀 이유:

1. **Flutter / React Native**

   NFC는 단순히 화면 UI를 구현하는 기능이 아니라 기기의 물리적 하드웨어 모듈과 통신해야 하는 기능이다. 멀티플랫폼을 사용하더라도 NFC를 다루기 위해서는 네이티브 API와 연결되는 플러그인이 필요하다. 이 경우 문제가 생겼을 때 원인이 프레임워크인지, 플러그인인지, 네이티브 코드인지 파악하기 어려울 수 있다고 판단해 우선순위에서 제외했다.

2. **Swift / iOS Native**

   iOS 사용자가 있는 만큼 고려했지만, Apple의 NFC 관련 정책과 실제 기기 테스트 조건이 MVP 단계에서는 부담이 되었다. 검증되지 않은 MVP를 위해 먼저 비용과 정책 제약을 감수하기보다는, 구현과 테스트가 가능한 Android Native를 우선 선택하는 것이 적절하다고 판단했다.

3. **RFID**

   RFID를 사용하려면 별도의 카드나 인증 수단을 개인에게 발급해야 할 가능성이 높다. 이미 크루들이 카드키를 사용하고 있는 상황에서 또 다른 수단을 챙겨야 한다면 오히려 번거로움이 늘어날 수 있다고 판단했다. 반면 NFC는 대부분의 스마트폰에 기본적으로 포함되어 있어 사용자가 이미 가지고 있는 기기를 인증 수단으로 활용할 수 있다는 장점이 있었다.

4. **GPS**

   GPS는 실내에서 오차 범위가 크고, 위치 조작 가능성도 있어 출석 인증 수단으로는 신뢰도가 낮다고 판단했다. 우리가 해결하고자 한 문제는 “이 사람이 실제 캠퍼스 공간에 있는가”를 확인하는 것이었기 때문에, GPS보다 특정 공간에 설치된 NFC 태그를 인식하는 방식이 더 적절하다고 보았다.

### 가장 크게 깨진 가설

* 무엇이었는가:

가장 크게 깨진 가설은 **“NFC 방식은 기존 출석 방식을 대체할 만큼 충분히 간단하고 편리할 것이다”**라는 가설이다.

처음에는 NFC를 태그하는 방식이기 때문에 기존의 `앱 실행 → 와이파이 연결 대기 → 출석 화면 진입 → 버튼 클릭` 과정보다 훨씬 간단할 것이라고 예상했다. 그래서 사용자가 NFC 방식을 기존 방식보다 더 편하게 느끼고, 기존 출석 방식을 대체할 수 있을 것이라고 생각했다.

* 어떻게 받아들였는가:

실제 사용자 피드백을 통해 NFC 방식이 단순히 “태그만 찍으면 되는 편한 방식”으로만 받아들여지지는 않는다는 것을 알게 되었다.

특히 여러 사람이 같은 시간대에 몰릴 경우 태그 앞에서 대기 시간이 생길 수 있고, NFC 태그가 설치된 물리적인 장소로 이동해야 한다는 점이 새로운 제약으로 인식되었다. 또한 NFC를 사용하더라도 앱 실행이 필요하거나, 실제 출석 서버가 사내망 조건에 의존한다면 최종 출석 처리에서 기존 네트워크 문제가 다시 발생할 수 있다는 점도 확인했다.

그래서 이 가설을 완전히 맞았다고 보기보다는, **NFC는 기존 출석 방식을 대체하는 수단이 아니라 보완하는 수단으로 보는 것이 더 적절하다**고 받아들였다.

이를 바탕으로 방향을 “기존 앱 방식을 없애고 NFC로 대체하자”에서 “기존 버튼 방식은 유지하되, 앱 접속이나 네트워크 인식이 불안정한 상황에서 NFC를 함께 사용할 수 있도록 하자”로 수정했다.

### 끝까지 검증 못 한 가설 (있다면)

* **NFC를 실제 운영 환경에 적용했을 때 병목 현상이 어느 정도로 발생할지**는 끝까지 직접 검증하지 못했다.

중간 공유 이후 더 많은 사용자를 대상으로 동시 사용 테스트를 진행하고, NFC 방식과 기존 버튼 방식을 병행했을 때 병목이 얼마나 줄어드는지 확인하고자 했다. 하지만 실제 운영 수준의 인원과 환경을 재현하기 어려워 직접적인 검증까지는 진행하지 못했다.

다만 사용자 인터뷰와 팀 논의를 통해 병목이 발생할 수 있는 원인은 정리할 수 있었다. NFC 태그 개수의 한계, 등교 시간대에 사람이 한 번에 몰리는 문제, 태그 설치 위치가 특정 동선에 집중되는 문제가 병목의 주요 원인이 될 수 있다고 판단했다.

따라서 이 가설은 아직 **불명확**한 상태로 남았다. 이후에는 층별 또는 마을별로 NFC 태그를 분산 배치하고, 지점당 2~3개의 태그를 설치한 뒤, 기존 버튼 방식과 병행했을 때 실제 대기 시간이 얼마나 발생하는지 추가로 검증해야 한다.
